## Загальне завдання

Модернізувати попередню лабораторну роботу (перевантаження операторів) для реалізації парадигм наслідування та динамічного поліморфізму в ієрархії класів:
* **Базовий клас прикладної галузі (`Phone`) зробити абстрактним**, додавши чисто віртуальні методи.
* **Додати класи-спадкоємці** відповідно до індивідуального завдання, які поширюють функціонал базового класу.
* **Забезпечити обов'язкове використання ключових слів `override` та `final`** у функціях базового класу та класів-спадкоємців.
* **Клас-список (`List`) повністю переробити** для роботи як з базовим абстрактним класом, так і з його спадкоємцями за допомогою механізму *динамічного зв'язування*. 
* Серед полів класу-списку повинен зберігатися **лише один гетерогенний масив вказівників**, що містить усі типи об'єктів ієрархії. Оновити методи взаємодії з цим масивом (копіювання, очищення, введення/виведення).
* Переконатися, що оператори введення / виведення (`<<`, `>>`) працюють коректно і поліморфно для всіх класів ієрархії, використовуючи текстові маркери фактичних типів.
* Навести в документації та звіті UML-діаграму розробленої ієрархії класів.

**Додаткові обов’язкові умови виконання робіт:**
* Повна відмова від використання глобального простору імен (`using namespace std;`) на користь точкових імпортів (наприклад, `using std::string;`).
* Повна відмова від C-бібліотек введення/виведення та рядків типу `char*` (виключно `std::string` та стандартні об'єктні потоки).
* Оформлення документації коду за допомогою утиліти Doxygen.
* Покриття розроблених поліморфних методів модульними тестами (Google Test Framework) не менше ніж на 50%.
* Демонстрація повної відсутності витоків пам'яті (`0 leaks`) за допомогою утиліти Valgrind.

## Індивідуальне завдання (Варіант 18)

1. **Базовий клас:** «Мобільний телефон» (`Phone`).
2. **Клас-спадкоємець 1:** «Кнопковий телефон» (`ButtonPhone`). Додаткові поля:
   * Чи є бабусяфоном (`bool isGrandpaPhone`).
   * Кількість кнопок (`int buttonCount`).
3. **Клас-спадкоємець 2:** «Складаний телефон» (`FoldingPhone`). Кінцевий у наслідуванні (`final`). Додаткові поля:
   * Чи складається телефон навпіл (`bool isFoldInHalf`).
   * Розмір екрану у складеному стані (структура `ScreenSize`).

**Реалізувати 3 обов'язкові методи для роботи з колекцією:**
1. Розрахувати загальний об’єм оперативної пам’яті (RAM) усіх пристроїв у списку.
2. Знайти кнопкові телефони, що НЕ є бабусяфонами (поліморфна фільтрація через `dynamic_cast`).
3. Знайти всі складані телефони в колекції.

## Структура проекту

* `uml.png` — графічна UML-діаграма класів, яка відображає відношення наслідування між `Phone`, `ButtonPhone`, `FoldingPhone` та відношення агрегації з контейнером `List`.
* `src/entity.h` / `src/entity.cpp` — оголошення та реалізація абстрактного класу `Phone` (із чисто віртуальними методами `getType()` та `clone()`), а також класів-спадкоємців `ButtonPhone` та `FoldingPhone`. Реалізація поліморфної серіалізації `toString()` / `fromString()`.
* `src/list.h` / `src/list.cpp` — опис та реалізація класу-контейнера `List`, який керує єдиним масивом вказівників `Phone** data`. Реалізує глибоке копіювання за *Правилом трьох* через віртуальне клонування об'єктів, логіку `dynamic_cast` для фільтрації варіанта, а також поліморфне відновлення об'єктів з файлу за маркерами типів (`BUTTON|...`, `FOLDING|...`).
* `src/main.cpp` — головний файл програми, що демонструє роботу з гетерогенною колекцією: наповнення об'єктами різних типів у динамічній пам'яті, виконання 3-х розрахункових завдань варіанта, збереження списку у файл та його повне відновлення.
* `test/test.cpp` — модульні тести (Google Test) для перевірки поліморфної поведінки: сумування пам'яті, коректність відпрацювання фільтрів `dynamic_cast`, глибоке копіювання списку без ефекту зрізання типів (*object slicing*) та файловий ввід/вивід.
* `Makefile` — скрипт автоматизації компіляції (`clang++`), тестування, аналізу витоків пам'яті та генерації документації.
* `Doxyfile` — конфігурація для генерації документації Doxygen.

## Інструкція з компіляції та запуску

Для автоматизованої взаємодії з проектом використовуйте наступні команди `make`:

* `make run` — повне очищення, компіляція проекту та запуск демонстраційного додатка (`main.bin`).
* `make test` — збірка та запуск модульних тестів за допомогою Google Test, перевірка бізнес-логіки та генерація звітів про покриття коду.
* `make leak-check` — запуск програми під керуванням утиліти `valgrind` для перевірки відсутності витоків пам'яті (критично для перевірки виклику віртуальних деструкторів).
* `make format` — генерація документації Doxygen на основі коментарів у коді.
* `make clean` — видалення тимчасових об'єктних файлів, бінарників та папки `dist`.
